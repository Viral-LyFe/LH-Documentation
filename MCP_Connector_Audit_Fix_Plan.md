# MCP Connector Security Audit — Fix & Study Plan

> Source: `LyfeHardwareMCPConnectorAuditReport.docx` (audit of `lh` app + `Viral-LyFe/mcp` fork, commit `dc3ae7f`)
> Overall score: **3.4/10 — NOT READY FOR PRODUCTION USE**
> Prepared: 2026-08-07

## Scope of the Audit

- **Audited**: two design documents, the `lh` app code, and the private MCP server fork.
- **Not audited**: the live ERPNext site (no access), and 12 of the 24 exposed record types belonging to external apps.
- **Confirmed good**: read-only guarantee holds (no write tools found), no shared service account, disabling a user blocks Claude access instantly, settings/credential screens are unreachable, financial dashboards are Super-Admin-locked, no SQL injection found, audit log can't be edited/deleted via UI, server library up to date with upstream.

The core finding: the "only shows what you could already see" half of the design is broken — masking hides a field's value in the response but doesn't stop it being filtered/sorted on, so it can be inferred anyway. That undermines most other protections.

Read/trace these before making changes, in this order:

## Post-Audit Policy Addition (2026-08-11) — Super Admin gets zero restriction via MCP

Not one of the original 28 audit issues — a new explicit instruction given after the audit and its self-audit were both closed: **"Any Activity in MCP by Super Admin Should have all access of all fields and doc, not restriction at all."**

**Investigated before implementing** (rather than assuming the existing DocPerm grants already satisfied this): checked every doctype this session added permlevel masking to (`Lyfe Order`, `Item`, `Quotation`, `Employee`, `MCP Audit Log`) for whether Super Admin was actually granted at every permlevel. Found **one real gap**: `Quotation`'s permlevel-1 grant (the shipping-rate section — `ignore_pricing_rule`, `custom_shipping_rate_final`, `custom_shipstation_carrier`, etc.) included `Maintenance Manager`/`Maintenance User`/`Sales Manager`/`Sales User`/`Factory`/`System Manager` but **not Super Admin** — a real Super Admin user (not just `Administrator`) was silently masked from those fields via `get_quotation`/`list_quotation` before this fix. Every other permlevel grant this session created already included Super Admin.

**Scope decided with the user:** the exemption applies to field masking, the Settings/Single-doctype block, the filter/sort-inference guard, AND the 200-row list cap — full "zero restriction," not just field visibility.

**Fix — structural, not just data-layer:**
- New shared helper `_is_super_admin_or_administrator()` in `doctypes.py` — true for the literal `Administrator` user OR anyone holding the `Super Admin` role. This is now the single check every enforcement point in that module calls, so the exemption is a property of the code, not dependent on any doctype's `Custom DocPerm`/`DocPerm` rows remembering to include Super Admin at every permlevel (exactly the class of gap the Quotation finding proved could happen silently).
- `_require_not_single()` (Settings-doctype block) — consolidated its existing two-line Administrator/Super-Admin check into the shared helper (no behavior change, just de-duplication).
- `_strip_masked_keys()` (field masking, both `get_<doctype>` and `list_<doctype>`) — was Administrator-only before; now also exempts Super Admin structurally.
- `_require_no_masked_filter_or_sort()` (filter/sort-inference guard) — was Administrator-only before; now also exempts Super Admin, since there's nothing left to infer around once nothing is masked from that role.
- `_clamp_list_limit()` (200-row cap) — had **no** exemption at all before this fix, for any role including Administrator; now Super Admin/Administrator's `limit` (including `0`/unset, meaning "no cap," matching Frappe's own `DatabaseQuery` behavior) passes through completely unmodified. `offset` is still normalized to a non-negative int for both — basic input sanitation, not a data-visibility restriction, left in place per explicit scope discussion.
- New patch `lh.patches.grant_super_admin_quotation_permlevel_one` — belt-and-braces fix of the one real missing DocPerm grant found, so the Desk-permission layer is correct too, not just the MCP-specific code exemption.

**Verified live end-to-end** with a real Super Admin user (`ravin@lyfehardware.com`, holds `Super Admin` but deliberately tested against fields gated to roles they don't otherwise hold, to isolate the exemption from any other grant):
- `Item.cost_of_goods_sold` (permlevel 1, Factory + Super Admin only) — visible via `get_item`, confirmed with a Super Admin user holding no Factory role.
- `Quotation.custom_shipping_rate_final` (the actual gap found) — visible via `get_quotation` after the fix; was masked before.
- `_require_not_single("ShipStation Settings")` — passes silently for Super Admin (no exception).
- `_clamp_list_limit({"limit": 0})` for Super Admin — `limit` stays `0` (uncapped), vs. clamped to `1` for an ordinary role.
- `_require_no_masked_filter_or_sort()` on a masked field — passes silently for Super Admin, still blocks an ordinary role.
- Confirmed every non-Super-Admin role's restrictions are completely unaffected — re-ran the same checks against an Engineer-only user and got the expected blocks in every case.

**Test-suite fallout, all expected and corrected, not regressions:** two existing test files had baked-in assumptions this change correctly broke — `test_mcp_field_masking.py`'s row-limit tests ran as `Administrator` (now also exempt, so the cap-testing assertions needed a non-privileged test user instead, plus new tests added for the bypass itself) and `test_quotation_item_cogs_permlevel.py`'s exact-role-set assertion at permlevel 1 needed `Super Admin` added to the expected set (the real gap this whole feature was built to close).
